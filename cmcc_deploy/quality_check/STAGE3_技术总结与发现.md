## 🔬 关键技术发现

### 发现 1：Qwen3.5 思维链问题 ⭐⭐⭐

**问题**：
- Qwen3.5-9B 是类 OpenAI o1 的推理模型
- 默认输出 "Thinking Process:"，每次生成 256 tokens
- 导致推理时间 10+ 秒，完全无法用于生产

**根本原因**：
```jinja
# chat_template.jinja (第 149-153 行)
{%- if enable_thinking is defined and enable_thinking is false %}
    {{- '<think>\n\n</think>\n\n' }}
{%- else %}
    {{- '<think>\n' }}  # 👈 默认启用思维链
{%- endif %}
```

**解决方案**：
```python
# 在 apply_chat_template 时传入 enable_thinking=False
text = processor.apply_chat_template(
    messages,
    tokenize=False,
    add_generation_prompt=True,
    enable_thinking=False  # 🔑 关键参数
)
```

**效果**：
- 推理时间：10,695 ms → 597 ms（**17.91x**）
- 输出 tokens：256 → 10-15（减少 94%）
- Caption 质量：100% 成功移除相机词汇

**重要性**：
- ⭐⭐⭐ 极高：这是本次部署最关键的优化
- 该发现具有通用性，适用于所有 Qwen3.5 系列模型
- 文档化价值高，可避免其他项目重复踩坑

### 发现 2：UniMatch 推理参数长度陷阱 ⭐⭐

**问题**：
```python
# ❌ 错误：参数长度不匹配
model(img1, img2, 
      attn_splits_list=[2],      # 长度 = 1
      corr_radius_list=[-1],      # 长度 = 1
      prop_radius_list=[-1]       # 长度 = 1
)
# AssertionError: len(attn_splits_list) == self.num_scales (2)
```

**根本原因**：
- UniMatch 模型配置 `num_scales=2`
- 所有推理参数列表长度必须 = 2
- 官方示例代码未明确说明此要求

**解决方案**：
```python
# ✅ 正确：所有列表长度 = num_scales
INFERENCE_PARAMS = {
    'attn_type': 'swin',            # 必需
    'attn_splits_list': [2, 8],     # 长度 = 2
    'corr_radius_list': [-1, 4],    # 长度 = 2
    'prop_radius_list': [-1, 1],    # 长度 = 2
}
```

**重要性**：
- ⭐⭐ 中等：容易踩坑，但一旦发现容易解决
- 文档化建议：在部署手册中明确标注

### 发现 3：DOVER 离线模式配置 ⭐⭐

**问题**：
- DOVER 依赖 timm 库，timm 会自动下载 convnext 预训练权重
- CMCC 机器无外网，导致初始化卡住

**解决方案**：
```bash
# 设置 PyTorch 缓存路径
export TORCH_HOME=/root/work/david_work/cache/torch

# PyTorch 会自动从 $TORCH_HOME/hub/checkpoints/ 加载权重
# 确保该路径下有 convnext_tiny_1k_224_ema.pth (110 MB)
```

**关键依赖**：
```bash
pip install scikit-video  # 必需，容易遗漏
```

**重要性**：
- ⭐⭐ 中等：离线环境必需配置
- 适用场景：所有使用 timm 库的项目

### 发现 4：H100 性能超预期 ⭐

**观察**：
- UniMatch 在 H100 上比预期快 10 倍
- 真实视频测试性能**优于**随机数据测试（28ms vs 35ms）

**可能原因**：
1. H100 的 Tensor Core 对小模型（4.7M 参数）优化极好
2. 真实视频的数据局部性更好（帧间相似度高）
3. CUDA 编译缓存对连续推理有加速效果

**启示**：
- 在高端 GPU 上，性能预估应基于实测而非理论计算
- 真实数据测试比合成数据更重要

## 🛠️ 最佳实践总结

### 实践 1：模型部署前必做预热测试

**教训**：
- Qwen3.5 在升级 transformers 后才能加载
- 但升级后的默认行为（思维链）完全不可用
- 如果没有预热测试，48 GPU 全量跑完才发现问题，损失巨大

**建议流程**：
1. 单样本加载测试（验证兼容性）
2. 单样本推理测试（验证性能）
3. 小批量测试（100 样本，验证稳定性）
4. 全量执行

**优先级排序**（基于本次实践）：

### 决策 2：分辨率选择

**选项**：
- 256×256：最快，但可能影响质量判断准确性
- 480×480：平衡，推理时间增加 3-4x
- 原始分辨率：最准确，推理时间增加 7-10x

**建议**：
- 先用 256×256 跑通
- 抽样验证质量
- 如不满意再升级分辨率

---

### 决策 3：Caption 改写范围

**当前策略**：仅改写包含相机词汇的 caption

**问题**：
- 如何判断是否包含相机词汇？

  - 全部过 VLM（准确但慢 2x）

**建议**：
- 先用关键词匹配
- 记录统计数据（有多少样本被改写）
- 根据结果决定是否调整策略
