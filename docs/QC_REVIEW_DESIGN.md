## 1. 背景与目标

### 我们在做什么

SANA-WM 是一个**世界模型训练数据标注管线**。它的作用是：把各类视频自动处理成带有精确摄像机轨迹标注的训练样本，用于训练 AI 理解三维世界。

管线已在 CMCC（中移动云算力平台，6 机器 × 8 H100 = 48 H100）上完成批量生产，产出约 **20 万条**训练样本，覆盖 7 个数据集 Group。

### 为什么需要质检

批量自动生产不可能 100% 完美。SLAM 算法在某些场景下会失败（画面过暗、运动过快、镜头切换），同时论文作者在发布 SANA-WM 时对训练数据做了严格的多维度过滤——不仅是位姿质量，还包括视频画质、运动合理性、内容适宜性。本次质检方案将这部分补齐。

### 质检的三个目标

1. **自动过滤**：把明显有问题的样本自动标记为"拒绝"，不进入训练集
2. **Caption 自动改写**：对含摄像机动作词的 caption 由 Qwen VLM 自动改写，改写结果存入 sidecar（不改原始数据）
3. **质量报告 + 人工复核触发**：产出可视化报告和人工审核队列，**人工审核在所有自动化阶段完成后进行**

## 2. 数据是什么，长什么样

### 每条样本包含 6 个文件

| 文件 | 内容 | 说明 |
|------|------|------|
| `{id}.mp4` | 归一化视频 | 1280×720 分辨率、16 帧/秒 |
| `{id}.poses_c2w.npy` | 摄像机轨迹 (T, 4, 4) | 每帧的 c2w 位姿矩阵 |
| `{id}.intrinsics.npy` | 内参 (T, 1, 4) | 每帧的 [fx, fy, cx, cy] |
| `{id}.scale.npy` | 度量尺度 (T,) | Default 模式固定为 1.0 |
| `{id}.caption.txt` | 场景描述 | 高质量英文静态场景描述 |
| `{id}.meta.json` | 来源元数据 | 数据集、场景 ID、帧数 T 等 |

样本以 **WebDataset tar 压缩包格式**（shard）存储于 CMCC externalstorage，每个 tar 包含若干样本。

## 3. 我们已经看到了什么问题

在设计质检方案前，我们抽取了 4 条 OmniWorld-Game 生产样本进行人工审阅：

### 发现一：摄像机轨迹存在"瞬移"跳变

每条游戏样本都有 **5~12 次**超过 50 厘米的单帧跳变：

| 样本 | 帧数 | 跳变次数（>50cm） |
|------|------|-----------------|
| 样本 A | 782 帧 | 5 次 |
| 样本 B | 3344 帧 | 5 次 |
| 样本 C | 2364 帧 | 10 次 |
| 样本 D | 1745 帧 | 12 次 |

游戏镜头切换是合理行为，但超出上限则说明 SLAM 跟踪失败——因此游戏类和真实世界类使用不同的容忍阈值。

### 发现二：同场景多片段共用同一条 caption

这是管线设计行为（caption 按场景生成），但 caption 中的弱框架词（"camera stays behind the character"、"third-person view"）经核查**不属于**论文禁止的强动作词，可直接保留。

### 发现三：游戏场景坐标尺度极大（最大 296m）

这是游戏虚拟世界的正常现象，不是质量问题。

## 4. 论文规定的过滤体系（原始标准）

### 4.1 两大类过滤

**类别 A：摄像机专项过滤**（适用所有数据集）

| 指标 | 论文规定 | 实现状态 |
|---|---|---|
| 视野角（FoV） | 水平和垂直均在 25°～120° | ✅ Stage 1 已覆盖 |
| 焦距一致性 | fx 与 fy 的归一化差异 ≤ 0.20 | ✅ Stage 1 已覆盖 |
| 尺度变异系数 | std/mean ≤ 2.0 | ✅ Stage 1 已覆盖（含 scale_cv 专项 hard-fail）|
| 位姿平滑度 | 连续帧间无大跳变 | ✅ Stage 1 已覆盖（跳变次数计数）|

| Caption 无摄像机动作词 | 文本匹配 | ✅ 已覆盖 | Stage 1 |
| 视频帧数核验 | PyAV | ✅ 已覆盖 | Stage 2 |
| 轨迹冻结检测 | 位移统计 | ✅ 已覆盖 | Stage 2 |

### 4.3 Caption 规范：禁止强动作词

论文第 4.4 节规定：caption 必须是静态场景描述，不能包含摄像机运动词语。

| 类型 | 示例 | 处理方式 |
|---|---|---|
| **强动作词**（触发改写）| "camera pans left"、"zooms in"、"dolly forward"、"tilt up"、"camera tracks" | Stage 1 检出 → Stage 3 Qwen 自动改写，结果写入 sidecar |
| **弱框架词**（允许保留）| "camera stays behind"、"third-person view"、"camera follows" | 不触发，描述的是拍摄视角而非主动运动 |

## 5. 质检策略总体设计

### 核心原则

> **所有自动化阶段（Stage 1 → Stage 2 → Stage 3）必须全部完成后，才启动人工审核。**

人工审核不是中间环节，而是最终的"最后一公里"兜底工序，针对机器无法确定性判断的边界样本。这样设计的原因：
- Stage 3 会进一步升级部分 Stage 1/2 通过的样本为"拒绝"（table6 不达标）
- Stage 3 会自动改写部分 caption（减少人工 caption 改写量）
- 只有拿到三个阶段的完整结论，人工队列才是最终的、最小化的

### 整体架构：三阶段自动化 → 人工收尾

```
20 万条样本（WebDataset tar shard 格式）
         │
         ▼
┌─────────────────────────────────────────────────┐
│  Stage 1：全量快速扫描（约 2 分钟，纯 CPU）       │
│  · 11 项检查：结构 / 位姿 / 颜色 / caption 文本   │
│  · 32 核并行处理所有 tar shard                   │
│  · 产出：每条样本的初步 verdict（pass/flag/fail）  │
└─────────────────────────┬───────────────────────┘
                          │
        ┌─────────────────┴──────────────────┐
        ▼                                    ▼
  pass（~75%，估计）                   flag + 随机抽 5% pass
        │                                    │
        │                                    ▼
        │             ┌─────────────────────────────────────┐
        │             │  Stage 2：深度检测（约 4~10h，CPU）  │
        │             │  · 仅处理 flag 样本 + 5% 抽检        │
        │             │  · 4 项检查：视频帧数 / 场景切割 /   │
        │             │    黑帧比例 / 轨迹冻结               │
        │             │  · 可更新 flag/fail 结论             │
        │             └─────────────────────────────────────┘
        │                                    │
        └─────────────────┬──────────────────┘
                          ▼
┌─────────────────────────────────────────────────────────────┐
│  Stage 3：GPU 密集型评估（约 6~7h，48 × H100，必做）        │
│  · 全量非 fail 样本                                          │
│  · UniMatch 光流 + DOVER 质量评分 + Qwen3.5-27B VLM         │
│  · Caption 含强动作词 → Qwen 自动改写（捆绑推理）            │

                          │

         │  产出物汇总（report.html 等）   │
```

## 6. 第一阶段：全量快速扫描（11 项检查）

Stage 1 对 20 万条样本全量扫描，全部基于 CPU，每条约 15~20 毫秒，32 核并行约 **2 分钟**完成。

### 检查 1：文件完整性

**检查内容：** 6 个文件全部存在，且可正常加载（不含空文件）。

**判定：** 任一文件缺失或加载报错 → **直接拒绝**。

---

### 检查 2：数值合法性（无 NaN / 无 Inf）

**检查内容：** 扫描 poses、intrinsics、scale 数组，确认不含 NaN 或 Inf。

**为什么重要：** SLAM 失败时会在输出中写入 NaN，这类值进入训练会导致梯度爆炸。

**判定：** 存在非有限值 → **直接拒绝**。

---

### 检查 3：帧数一致性（T 对齐）

**检查内容：** 确认 poses.shape[0] == intrinsics.shape[0] == scale.shape[0] == meta["T"]。

**判定：** 任意两者不一致 → **直接拒绝**。

---

### 检查 4：旋转矩阵合法性（SO(3) 验证）

**检查内容：** 每帧旋转矩阵的行列式 ≈ 1.0（偏差 < 0.001），且转置乘以自身 ≈ 单位矩阵（误差 < 0.001）。

**判定：** 不满足 → **直接拒绝**。

---

### 检查 5：首帧归零验证

**检查内容：** 第 0 帧必须是单位矩阵（坐标原点），最大偏差 < 0.01。

**依据：** 论文附录 D.3"first-frame anchor"规范。首帧归零使不同场景轨迹可比，是世界模型学习相对运动的前提。

**判定：** 偏差 > 0.01 → **直接拒绝**。

---

### 检查 6：摄像机位姿完整质量（含 scale_cv 验证）

**检查内容（委托 `evaluate_pose_quality()` 统一执行）：**
- **视野角（FoV）**：水平和垂直视野角均须在 25°～120°
- **焦距一致性**：fx 与 fy 归一化差异 ≤ 0.20
- **尺度变异系数（scale_cv）**：std(scale) / mean(scale) ≤ 2.0

**为什么 scale_cv 必须是 hard-fail：** scale_cv 过大意味着帧间度量尺度剧烈波动，SLAM 的深度估计发生了漂移——这类样本的轨迹与视频内容已脱钩，无法用于训练。

**判定：** 任一子项不满足（`pose_quality_ok = False`）→ **直接拒绝**。

---

### 检查 7：轨迹跳变计数（位姿平滑度近似）

**检查内容：** 计算每两帧间摄像机平移的 L2 距离，统计超过阈值的"大跳变"次数。

**判定逻辑（按数据集类型差异化）：**
- 跳变次数 > max_jumps_fail → **直接拒绝**
- 跳变次数 > max_jumps_flag → **标记待定（flag）**
- 其余 → 通过

各数据集具体阈值见[第 9 节](#9-差异化阈值策略按数据集分类)。

---

### 检查 8：颜色饱和度（论文 Table 6）

**检查内容：** 计算视频各帧 HSV 颜色空间中 S 通道（饱和度）的均值，范围 [0, 180]。

**适用范围：** 仅对真实世界类数据集启用（DL3DV / Sekai Walking / SpatialVID / RealEstate10K）；游戏类数据集（OmniWorld / Sekai Game Drone / Sekai Game Walking）不做此检查。

**饱和度极低（< 5）的含义：** 相机遮挡 / 夜间过暗 / 视频压缩损坏，SLAM 跟踪可靠性低。

**判定：** 超出数据集配置范围 → **标记待定（flag）**（不直接拒绝，因为可能是合理场景特性）。

---

### 检查 9：Caption 强动作词检测（论文 §4.4）

**检查内容：** 使用短语级正则匹配，检测 caption 是否包含描述摄像机主动运动的词语：
- `pan(s/ned/ning) left/right`
- `tilt(s/ed/ing) up/down`
- `zoom(s/ed/ing) in/out`
- `dolly`
- `camera moves/tracks/follows/sweeps/pushes/pulls`
- `camera pan/tilt/roll/orbits`
- `tracking/follow shot`

**注意：** 使用短语级（而非单词级）匹配以避免误判，"camera stays behind" 等弱框架词**不会触发**。

**判定：** 检出强动作词 → **标记待定（flag）**，在 Stage 3 由 Qwen 自动改写，不需要人工介入。

---

### 检查 10：Caption 基础质量

**检查内容：** Caption 不为空、不是占位符（"n/a"、"none"、"tbd" 等）、长度 ≥ 50 字符。

**判定：** 不满足 → **标记待定（flag）**。

---

### 检查 11：轨迹基本统计（信息收集）

**收集内容：** 轨迹总长度（m）、平均帧间步长（m）、最大单步跳变（m）、跳变次数、fx 均值。这些指标仅写入结果 JSONL 用于报告生成，不单独作为判定依据。

---

### Stage 1 各判定汇总

| 检查项 | 失败 → 直接拒绝 | 失败 → 标记待定 |
|---|---|---|
| 文件完整性 | ✅ | — |
| 无 NaN/Inf | ✅ | — |
| 帧数一致（T 对齐）| ✅ | — |
| SO(3) 合法性 | ✅ | — |
| 首帧归零 | ✅ | — |
| 位姿完整质量（含 scale_cv）| ✅ | — |
| 跳变次数 > max_jumps_fail | ✅ | — |
| 跳变次数 > max_jumps_flag | — | ✅ |
| 颜色饱和度超范围（按 group）| — | ✅ |
| Caption 含强动作词 | — | ✅ |
| Caption 基础质量不达标 | — | ✅ |

## 7. 第二阶段：针对性深度检测（4 项检查）

### 哪些样本进入 Stage 2

| 来源 | 比例 | 原因 |
|---|---|---|
| Stage 1 flag 样本 | 100% | 需要更精确的判断 |
| Stage 1 pass 样本随机抽取 | 5% | 抽样验证，确认没有系统性漏检 |
| Stage 1 fail 样本 | 0% | 已确定拒绝，无需深入 |

**预估进入 Stage 2 的样本量：** 约 1.5 万 ~ 3 万条。

---

### 深度检查 1：视频帧数核验（PyAV）

**检查内容：** 实际解码视频，数出真实帧数，与 poses 帧数比对。

**为什么 Stage 1 不直接做：** 打开视频比读取 numpy 数组慢 10~50 倍。

**判定：** 视频帧数 ≠ poses 帧数 → **拒绝**。

---

### 深度检查 2：场景切割数量（PySceneDetect，论文 Table 6）

**检查内容：** 用 PySceneDetect 的 ContentDetector（阈值=27）检测视频中的镜头切换次数。

**适用范围：** 仅对 RealEstate10K（上限 ≤ 1 次）启用；其他 group 不做此检查（论文 Table 6 标注为"—"）。

**场景切割过多说明什么：** 不连续的镜头拼接导致 SLAM 在同一轨迹内对不同地点做了错误的连接。

**注意：** 若 PySceneDetect 检测本身失败，返回 -1，不纳入阈值判断，仅记录"scene_cuts_error"原因。

**判定：** 切割次数 > max_scene_cuts → **拒绝**。

---

### 深度检查 3：黑帧比例检测

**检查内容：** 逐帧计算灰度均值，统计均值 < 10/255 的帧占比。

**依据：** 论文 App. B.2 规定过滤"超过 30% 近空白帧"的视频。

**判定：** 黑帧占比 > 30% → **拒绝**。

---

### 深度检查 4：轨迹冻结检测

**检查内容：** 计算相邻帧间摄像机平移的 L2 距离，统计 < 0.1mm（1e-4 m）的帧占比。

**判定：** 超过 50% 的帧静止不动 → **拒绝**（SLAM 丢失跟踪后输出冻结位姿）。

## 8. 第三阶段：GPU 密集型视觉质量评估（必做）

> **决策已确认（2026-06-25）：** Stage 3 对所有非 fail 样本必做，48 H100 全量约 **6~7 小时**完成。Qwen 模型权重和生产数据已在 CMCC filestorage 就绪，无需额外下载。

### 处理范围

Stage 1 和 Stage 2 结束后，所有 verdict ≠ "fail" 的样本全部进入 Stage 3（包括 pass 和 flag）。

### 资源与耗时估算

| 指标 | 单样本耗时（H100）| 20 万条 / 48 卡并行 |
|---|---|---|
| UniMatch 光流 | ~3s | ~3.5 小时 |
| DOVER 质量评分 | ~0.5s | ~0.6 小时 |
| Qwen VLM（含 caption 改写）| ~2s | ~2.3 小时 |
| **合计（串行流水线）** | **~5.5s / 条** | **~6.4 小时** |

### CMCC 部署方式

采用 **worker-id 分片并行**：每张 GPU 卡运行一个独立 worker 进程，按 `idx % total_workers == worker_id` 的轮询方式分配样本，互不干扰：

```bash
# 每个 GPU 节点上独立运行（由 SSH launcher 派发）：
CUDA_VISIBLE_DEVICES=$gpu python scripts/run_stage3_cmcc.py \
  --stage1-jsonl .../stage1_results.jsonl \
  --output-dir   .../qc_output/wds-OmniWorld-Game/ \
  --qwen-dir     ~/work/filestorage/.../Qwen3.5-27B-VL/ \
  --unimatch-dir ~/work/filestorage/.../UniMatch/ \
  --worker-id $((NODE_RANK*8+gpu)) --total-workers 48 \
  --table6-cfg   .../configs/filter_thresholds.yaml
```

每个 worker 完成后写 `.done` 标志文件，支持断点续跑（重新执行自动跳过已完成的 worker）。

### 三项 GPU 指标说明

| 指标 | 检测内容 | 阈值来源 |
|---|---|---|
| **UniMatch 光流幅值均值** | 相邻帧间像素运动量。每 0.5 秒采样一对帧，取前 60 秒窗口均值。**替代 VMAF Motion**（两者物理含义相同，避免 libvmaf 依赖）。 | 论文 Table 6 UniMatch 列，各 group 不同 |
| **DOVER 质量评分** | 技术质量（模糊/噪声/压缩伪影）+ 美学质量（构图/光线）综合评分。每 5 秒一个切片，取均值。 | 论文 Table 6 DOVER 列，各 group 不同 |
| **Qwen3.5-27B VLM（捆绑实体计数 + 质量标记 + Caption 改写）** | 采样 8 个关键帧：① 统计场景中人/车/动物数量；② 给出整体视觉质量分；③ 若 Stage 1 已标记 caption 含强动作词，**在同一次推理中追加改写指令**，零额外成本。改写后的 caption 写入 `caption_overrides.jsonl` sidecar，**不修改原始 tar**。 | 论文 Table 6 VLM 列；改写指令来自论文 §4.4 |

### Table 6 评估与 fail 升级规则

Stage 3 在各指标计算完成后，调用 `apply_table6.evaluate(source, scores, cfg)` 统一评估：
- `table6_accepted == False` 且当前 verdict ≠ "fail" → **升级为 fail**，并将原因写入 flag_reasons

此规则确保最终 `reject.txt` 涵盖所有三个阶段的拒绝依据。

### Caption 改写 sidecar 说明

```
qc_output/
└── caption_overrides.jsonl    # 每行一条改写记录
    {"sample_id": "...", "caption_original": "...", "caption_revised": "..."}
```

训练团队在构建最终训练集时，以 `caption_overrides.jsonl` 覆盖对应样本的 caption，原始 tar 文件保持不变、可溯源。

## 10. 质检产出物清单

### 每条样本的最终状态

| 状态 | 文件 | 含义 |
|---|---|---|
| ✅ **pass** | pass.txt | 三个阶段全部通过，可直接进入训练集 |
| 🔴 **fail（reject）** | reject.txt | 存在明确不可挽救的质量问题 |
| 🟡 **flag（human review）** | human_review.txt | 机器无法确定性判断，送人工决策 |

**判定优先级：** 任一阶段触发 fail → 最终状态为 fail（Stage 3 table6 不达标会升级 pass/flag 为 fail）。

### 完整产出目录结构

```
qc_output/
├── stage1_results.jsonl          # Stage 1 每条样本详细检测记录
├── stage2_results.jsonl          # Stage 2 深度检测记录（flag + 抽检样本）
├── stage3_worker{id:03d}.jsonl   # Stage 3 每个 worker 的结果（48 个文件）
├── stage3_results.jsonl          # Stage 3 合并后的完整结果
├── caption_overrides.jsonl       # Caption 改写 sidecar（每条改写记录一行）
├── manifests/
│   ├── pass.txt                  # 通过样本 ID 列表（每行一个）
│   ├── reject.txt                # 拒绝样本 ID 列表（每行一个）
│   └── human_review.txt          # 人工审核队列（sample_id + tab + 原因说明）
└── report.html                   # 可视化质量报告
```

### HTML 报告内容

- **总体概览**：pass / fail / flag 数量与比例，三阶段覆盖情况
- **分 Group 汇总表**：每个数据集的通过率、拒绝率、待定率
- **关键指标分布图（SVG 直方图）**：跳变次数分布、DOVER 评分分布、UniMatch 光流分布
- **Caption 问题统计**：强动作词命中率、改写条数
- **人工审核队列预览**：前 200 条待定样本及具体原因

## 11. 人工审核环节（最后工序）

> **重要：人工审核只在 Stage 1 + Stage 2 + Stage 3 全部完成、最终 manifests 生成后才启动。**

### 为什么人工审核必须在最后

1. **Stage 3 会进一步拒绝样本**：部分在 Stage 1/2 "通过"的样本，经 Stage 3 table6 评估后会升级为 fail——若提前让人工审核这些样本，是在浪费人力。
2. **Stage 3 Qwen 会自动改写 caption**：Stage 1 标记的含动作词 caption 大多数可由 Qwen 自动处理，人工只需审核 Qwen 改写失败或结果不自然的极少数样本。
3. **最终 human_review.txt 才是净化后的最小审核队列**，避免中间状态造成的重复审核。

### 人工审核的任务

审核员拿到 `human_review.txt`（附带原因说明）后，对每条样本：

1. 查看**具体原因**（如"n_jumps=8 > flag 阈值"、"caption_word: 'pans left'"）
2. 可选：打开视频，直观确认
3. 给出**三选一结论**：
   - `approve`：确认通过，加入训练集
   - `reject`：确认拒绝
   - `caption_rewrite`：需人工改写 caption 后保留（此项应较少，Stage 3 已自动改写大部分）

### 人力估算

| 情景 | 待定率（Stage 3 后）| 待定样本数 | 人均速度 | 所需人力 | 工期（5 人）|
|---|---|---|---|---|---|
| 乐观 | 3% | 0.6 万条 | 200 条/小时 | 30 人时 | **不足 1 天** |
| 基准 | 10% | 2 万条 | 150 条/小时 | 133 人时 | **约 2~3 天** |
| 保守 | 20% | 4 万条 | 150 条/小时 | 267 人时 | **约 4~5 天** |

> **注：** Stage 3 完成后，部分原本 flag 的样本会升级为 fail（减少人工审核量），同时 caption 动作词类的 flag 大多已自动改写（进一步减少人工介入）。因此 Stage 3 后的实际待定率预计低于 Stage 1 结束后的估算。

### 最终交付

人工审核完成后，将自动质检结论（reject.txt）与人工审核的 approve 列表合并，生成：

```
pass_final.txt    # 最终可入训练集的样本 ID 列表
```

移交训练团队。

### 完整时间线（基准情景）


## 13. 部署注意事项与风险

### CMCC 环境补包清单（部署前必须完成）

| 包 / 资产 | 用途 | 阶段 | 状态 |
|---|---|---|---|
| `av`（PyAV） | 视频帧数核验 | Stage 2 | ⚠️ 需 `pip install av` |
| `scenedetect` | 场景切割计数 | Stage 2 | ⚠️ 需 `pip install scenedetect` |
| `dover` | DOVER 视频质量推理 | Stage 3 | ⚠️ 需 `pip install dover` + 权重 ~400MB |
| UniMatch 代码 + 权重 | 光流计算 | Stage 3 | ✅ 已在 filestorage（~200MB）|
| Qwen3.5-27B-VL 权重 | VLM 推理 + caption 改写 | Stage 3 | ✅ 已在 filestorage（~55GB）|

### 技术风险

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| CMCC tar shard 路径结构与 `--tar-root` 预期不符 | Stage 1 找不到文件 | 上线前用 `python scripts/run_qc.py --tar-root ... --n-workers 1` 对单个 group 的 1 个 shard 冒烟 |
| 某 Group 待定率远超 20% | 人工审核量暴增 | 先跑单 Group 看报告，阈值偏严可调整 max_jumps_flag（如从 0 调到 3）|
| PySceneDetect 在 CMCC conda 环境报错 | Stage 2 scene_cuts 字段返回 -1 | 已有防御处理：-1 不触发阈值比较，仅记录 "scene_cuts_error" 原因；不影响流水线继续 |
| Qwen3.5-27B 与 UniMatch/DOVER 在单卡 H100（80GB）同时加载 OOM | Stage 3 崩溃 | 各模型独立加载，串行推理（Qwen 约 54GB，其余 ~5GB，合计 < 80GB）；run_stage3_cmcc.py 已按此设计 |
| Stage 3 某 worker 中途崩溃 | 部分样本未处理 | `.done` 标志文件机制：重新运行只跳过已完成的 worker，崩溃的 worker 自动重跑 |
| UniMatch 光流阈值与论文 VMAF Motion 阈值不完全等价 | 少量误拒或误通过 | 首批生产后，用已知优质样本验证 UniMatch 分数分布，确认阈值合理性 |

### 决策状态（全部已确认）

| 问题 | 结论 |
|---|---|
| Stage 3 是否做？ | ✅ 全量必做，6~7 小时 |
| Caption 含动作词：丢弃还是改写？ | ✅ 两级检测 + Stage 3 Qwen 自动改写，零额外成本 |
| 游戏数据跳变上限？ | ✅ max_jumps_fail=50（OmniWorld/Sekai Game Walking）；无人机=80 |
| VMAF Motion 是否使用？ | ✅ 取消，用 UniMatch 光流幅值均值替代（物理意义相同，规避 libvmaf）|
| 人工审核顺序？ | ✅ 严格在 Stage 1+2+3 全部完成后才启动 |
